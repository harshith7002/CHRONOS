CORE PRINCIPLES

Architectural Invariants

Four foundational rules that ensure execution correctness under continuous change.

01
Version, Don't Overwrite
Every intent change creates a new immutable state snapshot (v1 → v2 → v3). Historical snapshots are never mutated.
02
Cancel Selectively
Only invalid work is cancelled. Reusable upstream computation and unaffected subtrees survive across updates.
03
Reject Stale Results
Every tool result is stamped with its origin snapshot ID. Late results from obsolete versions are discarded before state mutation.
04
Guard the Commit
Irreversible actions require triple verification: active snapshot binding, explicit confirmation, and idempotency deduplication.
DEPENDENCY ORCHESTRATION

Selective invalidation, not restart

CHRONOS invalidates only the affected dependency subtree instead of restarting the entire workflow.

Scenario: User changes selection criterion from "Cheapest" to "Earliest"
SEARCH ✓ PRESERVED (REUSED)
➔
FILTER ✓ PRESERVED (REUSED)
➔
SELECT ✕ INVALIDATED
➔
BOOK 🔒 BLOCKED
Because the destination did not change, the expensive SEARCH and FILTER results are preserved, while only the downstream SELECT and BOOK nodes are recalculated.
CORRECTNESS CONTRACT

Seven invariants keep execution safe

The implementation is designed around mathematical invariants rather than relying on probabilistic LLM behavior.

INV-1 Stale results cannot mutate active intent slots or completed state.
INV-2 Only the current active snapshot can commit irreversible actions.
INV-3 One idempotency key permits at most one irreversible commit.
INV-4 Invalidation of an upstream dependency invalidates all dependent downstream work.
INV-5 Superseded branches cannot execute new state-changing writes.
INV-6 Unconfirmed irreversible actions are strictly blocked from execution.
INV-7 Historical state snapshots are strictly immutable.
